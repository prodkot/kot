# Разработка и проверка версий

Обязательные правила стадий и приёмки для всех версий находятся в [LIFECYCLE.md](LIFECYCLE.md). Этот документ уточняет совместимость установщика и проверки на Windows, не заменяя критерии жизненного цикла. Порядок публикации находится в [GITHUB.md](GITHUB.md), а изменения версий перечислены в [CHANGELOG.md](../CHANGELOG.md).

## Установка и совместимость

Поддерживается обычное приложение `Kot.exe`, устанавливаемое и обновляемое через Setup. Данные остаются в `%LOCALAPPDATA%/KotVPN`. При обновлении с 0.6.1 сохраняются DPAPI-профиль, HWID, статистика, имя задачи автозапуска, идентификаторы окна и ярлыков, имя TUN и постоянные ключи WFP.

Setup содержит один подписанный ZIP с приложением. Мастер NSIS включает только небольшую нативную программу распаковки; она проверяет тот же пакет закреплённым ключом и устанавливает его через общий механизм с резервными копиями и откатом. Отдельная установка .NET для неё не нужна. Формат `KOT.SETUP.V1.END` и процесс обновления для пользователя сохранены, включая клиента 0.6.1. Для сборки этой программы нужны инструменты C++ из Visual Studio; само приложение WinForms не переводится на NativeAOT.

Временные варианты приложения, отдельные runtime, альтернативные пути профиля и связанные скрипты и проверки удалены. Telegram-прокси по-прежнему использует собственную папку `TgWsProxy_data` внутри управляемого пакета. Занятый драйвер WinDivert очищается после перезагрузки только из папки своего пакета; чужие драйверы не останавливаются.

## Локальная проверка в Dev

Dev является стадией активной разработки: новые функции, эксперименты, архитектурные изменения и переработка UI допустимы в рамках задачи. Промежуточные решения и ограничения явно описывай. Для внутренней локальной сборки выполни применимые автоматизированные проверки по [матрице](../docs/VALIDATION.md), отдельно перечисли ошибки, недоступные и невыполненные проверки.

Для локальной передачи Dev не запускай Actions и не публикуй полноценный релиз. Push в `dev/**` автоматически запускает Actions, поэтому локальную работу сохраняй на своей машине. Обычный авторизованный PR может запускать проверки исходников; это не публикация Dev и не приёмка Beta. Фильтр веток `dev/**` не задаёт канал версии.

## Beta в GitHub Actions

Beta предназначена для стабилизации: исправлений, полировки, совместимости и регрессий. Крупные новые функции требуют прямого разрешения владельца. При подготовке авторизованного CI-прогона задай в `Directory.Build.props` значение `Beta` для `KotChannel` и номер для `KotPrereleaseNumber` до отправки кандидата в `dev/**`.

Для полноценной Beta оба workflow ниже должны успешно завершиться на одном точном коммите. Обязательны реальные Windows WebView2, трей, DPI/масштабирование, TUN, запуск, завершение работы, установка, обновление, восстановление после сбоя и удаление, а также проверенный подписанный Setup из Actions. Отсутствующее покрытие workflow дополняй проверкой на Windows с фиксацией ревизии и результата. Пропущенный обязательный сценарий блокирует приёмку даже при зелёном итоге CI.

Локальная сборка без этих этапов является исключительно **локальным кандидатом Beta**. Называй её так при передаче и в отчёте. Компиляция WindowTests, переносимые тесты или Chromium не заменяют выполнение Windows-сценариев. Частично проверенный CI-артефакт также ещё не принятая Beta.

- **Windows checks** запускается при push в `main` и `dev/**`, а также для pull request. Он проверяет логику, интерфейс в браузере, нативное окно и WebView2, трей, процессы и официальные сборки управляемых сервисов.
- **Windows development build** запускается при push в `dev/**` или вручную на такой ветке: собирает Setup, проверяет настоящее подключение TUN, kill switch, установку, обновление и удаление.
- XHTTP проверяется на локальных TLS/REALITY-серверах, включая отдельный адрес скачивания и имена, известные только DNS Xray. Отдельная проверка воспроизводит отказ старого системного резолвера. На Windows дополнительно запускается настоящий `Tunnel.Connect` с глобальным kill switch: успешная передача HTTP, ошибка недоступного сервера, отмена, остановка обоих ядер и очистка временных конфигураций. Эти проверки не подтверждают доступность конкретного сервера в сети пользователя.
- Проверка упаковки запускает нативную распаковку в папку с пробелами и кириллицей, повторную установку, отказ при повреждении Setup и настоящий updater из опубликованной 0.6.1. Последний устанавливает новый пакет и ждёт подтверждения готовности WebView2; проверяются файлы, прежний зашифрованный HWID, настройки и статистика. Эта проверка запускается только в чистом тестовом аккаунте CI.
- Подписанный установщик кандидата Beta доступен в артефакте `windows-development` соответствующего запуска Actions. Сверь версию, коммит и хеш по [правилам передачи Setup](BUILD-IDENTITY.md). Срок хранения составляет 30 дней. Для скачивания GitHub может потребовать вход в аккаунт.
- Тестовый установщик заменяет установленный клиент. Для обычного использования предназначен Stable Setup из обычного GitHub Release, а не Beta Pre-release.

У workflow разработки только разрешение `contents: read`. Он не создаёт теги и GitHub Releases. Передача артефакта Actions не является публикацией. Публикация принятой Beta разрешена только как GitHub Pre-release, с явного разрешения владельца и по [отдельным правилам](GITHUB.md#публикация-beta). Завершение workflow разработки не запускает публикацию сайта, подписанную на **Windows release**. Браузерные проверки подтверждают интерфейс; проверки CI на Windows подтверждают только испытанные сценарии. Обход ограничений провайдера, Telegram, видео и голосовые вызовы требуют ручной проверки в реальной сети.

## Слияние и выпуск

Перед слиянием сверь публичную версию клиента в Core, Windows, интерфейсе и установщике. Первый раздел [CHANGELOG.md](../CHANGELOG.md) должен относиться к той же базовой версии и совпадать с [заметками версии](NOTES.md). Проверь результаты обоих workflow для итоговой ревизии Beta и сверь актуальную `main` на конфликты.

Для слияния в main нужно явное разрешение владельца проекта. Оно не заменяет отдельное разрешение на публикацию. Stable выпускается только после завершённой приёмки, без известных критических регрессий, из main как обычный GitHub Release. Публикация и замена уже опубликованного установщика требуют явного разрешения владельца на соответствующее действие. Порядок проверки стабильного Setup и публикации из `main` описан в [GITHUB.md](GITHUB.md). Сведения сайта о последнем опубликованном релизе обновляет **Website** после успешного выпуска.
