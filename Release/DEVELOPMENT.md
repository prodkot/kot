# Подготовка версии 0.7.0

Версия приложения и установщика **0.7.0** подготовлена в ветке `dev/0.6.2`. Этот документ описывает её разработку, совместимость и проверки; порядок выпуска из `main` находится в [GITHUB.md](GITHUB.md).

В 0.7.0 добавлено управление zapret и Telegram-прокси, подбор стратегий, обновлённые настройки, статистика и меню трея. Подробности и ограничения сетевых проверок описаны в [руководстве сервисов](../docs/SERVICES.md). Основной AppLog очищает записи до сохранения и хранит данные для скрытия только текущего профиля. Журналы приложения и сервисов ограничены.

## Установка и совместимость

Поддерживается обычное приложение `Kot.exe`, устанавливаемое и обновляемое через Setup. Данные остаются в `%LOCALAPPDATA%/KotVPN`. При обновлении с 0.6.1 сохраняются DPAPI-профиль, HWID, статистика, имя задачи автозапуска, идентификаторы окна и ярлыков, имя TUN и постоянные ключи WFP.

Setup содержит один подписанный ZIP с приложением. Мастер NSIS включает только небольшую нативную программу распаковки; она проверяет тот же пакет закреплённым ключом и устанавливает его через общий механизм с резервными копиями и откатом. Отдельная установка .NET для неё не нужна. Формат `KOT.SETUP.V1.END` и процесс обновления для пользователя сохранены, включая клиента 0.6.1. Для сборки этой программы нужны инструменты C++ из Visual Studio; само приложение WinForms не переводится на NativeAOT.

Временные варианты приложения, отдельные runtime, альтернативные пути профиля и связанные скрипты и проверки удалены. Telegram-прокси по-прежнему использует собственную папку `TgWsProxy_data` внутри управляемого пакета. Занятый драйвер WinDivert очищается после перезагрузки только из папки своего пакета; чужие драйверы не останавливаются.

## Проверки и тестовый установщик

- **Windows checks** запускается при push в `dev/**`: проверяет логику, интерфейс в браузере, нативное окно и WebView2, трей, процессы и официальные сборки управляемых сервисов.
- **Windows development build** запускается при push в `dev/**` или вручную на такой ветке: собирает Setup, проверяет настоящее подключение TUN, kill switch, установку, обновление и удаление.
- XHTTP проверяется на локальных TLS/REALITY-серверах, включая отдельный адрес скачивания и имена, известные только DNS Xray. Отдельная проверка воспроизводит отказ старого системного резолвера. На Windows дополнительно запускается настоящий `Tunnel.Connect` с глобальным kill switch: успешная передача HTTP, ошибка недоступного сервера, отмена, остановка обоих ядер и очистка временных конфигураций. Эти проверки не подтверждают доступность конкретного сервера в сети пользователя.
- Проверка упаковки запускает нативную распаковку в папку с пробелами и кириллицей, повторную установку, отказ при повреждении Setup и настоящий updater из опубликованной 0.6.1. Последний устанавливает новый пакет и ждёт подтверждения готовности WebView2; проверяются файлы, прежний зашифрованный HWID, настройки и статистика. Эта проверка запускается только в чистом тестовом аккаунте CI.
- После успешной сборки установщик доступен в артефакте `windows-development` соответствующего запуска Actions. Срок хранения - 30 дней. Для скачивания GitHub может потребовать вход в аккаунт.
- Тестовый установщик заменяет установленный клиент. Для длительного испытания 0.6.1 следует продолжать пользоваться именно её сборкой.

У workflow разработки только разрешение `contents: read`. Он не создаёт теги и GitHub Releases. Его завершение не запускает публикацию сайта, подписанную на **Windows release**. Браузерные проверки подтверждают интерфейс; проверки CI на Windows подтверждают только испытанные сценарии. Обход ограничений провайдера, Telegram, видео и голосовые вызовы требуют ручной проверки в реальной сети.

## Слияние и выпуск

Перед слиянием должны совпадать версия клиента в Core, метаданные Windows, установщик, интерфейс, первый раздел [CHANGELOG.md](../CHANGELOG.md) и [заметки версии](NOTES.md). Необходимо проверить успешные Windows checks и Windows development build именно для итогового коммита, а также повторно сверить актуальную `main` на конфликты.

После успешных проверок изменения объединяются с `main`. Для выпуска запускается **Windows release** из `main` с включённой публикацией: workflow создаёт тег `v0.7.0` и публикует проверенный установщик. Сведения сайта о последнем опубликованном релизе обновляются workflow **Website** после успешного выпуска.

Обычный порядок выпуска описан в [GITHUB.md](GITHUB.md).
