# Выпуск версии

Постоянные критерии каналов и приёмки определяет [LIFECYCLE.md](LIFECYCLE.md). Успешные проверки разрешают считать пройденным соответствующий этап, но не дают разрешения на публикацию, слияние в main или замену опубликованного Setup.

## Публикация Beta

1. Заверши приёмку по [DEVELOPMENT.md](DEVELOPMENT.md): оба Windows workflow на одном коммите, реальные Windows-сценарии и проверенный подписанный Setup из Actions. Локальный кандидат или частично проверенный CI-артефакт публиковать как принятую Beta нельзя.
2. Получи явное разрешение владельца на публикацию конкретной Beta. Сохрани ссылки на runs, коммит, версию, UTC-время, имя и SHA-256 проверенного Setup. Разрешение на сборку или тестирование не является разрешением на Pre-release.
3. Для разрешённой публикации используй только **GitHub Pre-release** с `prerelease=true` и тегом, соответствующим полной версии, например `v0.8.5-beta.2`. Тег должен указывать на проверенный коммит. Не назначай Beta статус Latest, не меняй стабильные ссылки скачивания и не снимай флаг prerelease для продвижения Beta в Stable. Прикладывай точные проверенные байты Setup из Actions, не локальную пересборку.
4. После публикации проверь флаг prerelease, целевой коммит, имя и SHA-256 опубликованного установщика. Стабильные обновления и страницы скачивания должны продолжать указывать на Stable.

**Ограничение текущей автоматизации:** `Windows development build` создаёт артефакт и имеет `contents: read`, но не публикует Pre-release. `Windows release` предназначен для Stable, а `Release/check-ref.py` запрещает ему публиковать prerelease. Отправка любого тега `v*` может запустить этот стабильный workflow; его нельзя использовать как способ публикации Beta или ослаблять его защиту. Путь публикации Beta должен быть отдельно подготовлен и проверен до разрешённой публикации, с учётом теговых триггеров. Пока такого пути нет, сохраняй принятую Beta в артефактах Actions; наличие артефакта не означает, что Pre-release опубликован. Эти правила документации сами по себе не добавляют новую автоматизацию.

## Публикация Stable

1. Заверши приёмку Beta в GitHub Actions по [инструкции для Beta](DEVELOPMENT.md). Для ревизии кандидата должны пройти оба workflow и все обязательные реальные Windows-сценарии. Проверь подписанный установщик, сохрани ссылки на результаты и убедись в отсутствии известных критических регрессий. Если после Beta изменились код клиента, зависимости или способ упаковки, проверь эти изменения в новой Beta.
2. Запиши изменения в `Release/NOTES.md` и `CHANGELOG.md`.
3. После успешного тестирования Beta получи явное разрешение владельца проекта на стабильный выпуск этой версии. Для стабильной версии сохрани базовый номер и очисти `KotChannel` и `KotPrereleaseNumber` в `Directory.Build.props`. Сверь производные версии клиента, интерфейса, Windows и установщика по [правилам передачи Setup](BUILD-IDENTITY.md).
4. Запусти `python Tests/repository.py`, проверки из [docs/BUILD.md](../docs/BUILD.md) и CI pull request. Проверь итоговый стабильный Setup на ветке PR через **Windows release** с выключенной публикацией. После успешных проверок и разрешения на слияние слей PR.
5. Для разрешённого выпуска открой **Actions → Windows release → Run workflow**, выбери ветку `main`, включи галочку **«Опубликовать новую версию из main в Releases»** и запусти workflow. После сборки и проверок он создаст тег `vНОМЕР` на том же коммите и опубликует установщик.

При выключенной галочке ручной запуск только собирает и проверяет установщик. Публикация Stable разрешена только из `main`, как обычный GitHub Release (`prerelease=false`), после завершённой приёмки и явного разрешения владельца. Существующий тег не перезаписывается. Тот же разрешённый выпуск можно опубликовать отправкой тега `vНОМЕР` на проверенном коммите `main`. Отправка тега запускает публикацию автоматически и требует тех же результатов Beta и явного разрешения владельца. Заранее создавать страницу релиза не нужно.

Перед сборкой workflow проверяет совпадение тега с версией клиента и принадлежность публикуемого коммита истории `origin/main`. Тег на неслитой ветке отклоняется. Для проверки истории checkout получает все коммиты; предварительная сборка PR без публикации остаётся доступной.

## Совместимость и подписи

Не заменяй опубликованный установщик без отдельного явного разрешения владельца. Новые байты требуют новой проверки происхождения, подписей и SHA-256. Успешный workflow не даёт разрешения менять уже опубликованные артефакты. Стабильный обновлятор и ссылки на последнюю стабильную версию не должны предлагать экспериментальные, Beta, RC или draft-выпуски. Текущий `Core/RemoteUpdates.cs` использует стабильный источник, исключает `draft/prerelease` до сравнения версии и ожидает стабильное имя Setup. Сохраняй этот контракт.

Историческая совместимость: в сборках `v0.8.0-xray.N` внутренняя версия клиента тоже `0.8.0`. Пользователям этих сборок нужно установить финальный `v0.8.0` новым Setup вручную: встроенный обновлятор предлагает только более высокий номер версии.

Workflow соберёт Setup и подпишет манифесты установщика и вложенного пакета RSA-ключом `KOT_RELEASE_SIGNING_KEY` из GitHub Secrets. Сам файл `.exe` выпускается без Authenticode, поэтому Windows может показать предупреждение SmartScreen. Workflow публикует один установщик и берёт текст страницы релиза из `Release/NOTES.md`.

Приватный ключ хранится вне репозитория. Его публичная часть уже закреплена в клиенте. Не заменяй ключ при обычном обновлении: предыдущие клиенты не примут новую подпись.

Для локальной проверки упаковки подписанного Setup на Windows нужны NSIS 3, Python 3, .NET 10 SDK, PowerShell 7 и Visual Studio 2022 или новее с компонентом **Desktop development with C++** для нативной программы распаковки и небольшой DLL оформления установщика:

```powershell
pwsh ./Release/release.ps1 -Key 'C:\private\kot-release.pem'
```

В `artifacts` останется только Setup. ZIP используется внутри сборки и встраивается в Setup один раз, отдельно не публикуется. NSIS содержит собственные страницы и небольшую нативную DLL оформления, шрифт Manrope, программу распаковки NativeAOT и команды ярлыков и удаления; второго комплекта файлов приложения в нём нет. Перед публикацией Setup повторно проверяется клиентским валидатором и нативной программой распаковки.

В CI сборка также проверяет обновление этим Setup через настоящий updater версии 0.6.1 с запуском нового WebView2. Локальная сборка не запускает эту проверку над обычным аккаунтом разработчика. Её можно выполнить отдельно в чистом тестовом аккаунте Windows через `Release/setup-checks.ps1 -Setup <exe> -Extractor <native-exe> -Publish <publish-folder> -Version <version> -LegacyUpdate`.
