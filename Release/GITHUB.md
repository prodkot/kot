# Публикация kot. и автообновления через GitHub

## 1. Подготовьте репозиторий

Создайте публичный репозиторий, например `USERNAME/kot`. В его корень загрузите **содержимое** папки исходников: Core, Windows, Tests, Installer, Release, .github, build.ps1, README.md и лицензии. Не помещайте их внутрь дополнительной папки Kot-Client-0.4.1. Не загружайте личные подписки, профили или приватный ключ. .gitignore уже подготовлен.

Официальный репозиторий: https://github.com/prodkot/kot. Сборка через workflow сама получает адрес из GITHUB_REPOSITORY. В ранее присланной сборке 0.4.0 можно один раз задать `prodkot/kot` в Настройки -> Обновления, источник GitHub. Либо установите сборку из Releases, в которой адрес уже встроен.

## 2. Ключ издателя и собственные сборки

Для официального `prodkot/kot` ключ подписи уже настроен как зашифрованный Actions secret `KOT_RELEASE_SIGNING_KEY`. Используется тот же ключ, которому доверяет ранее присланная версия 0.4.0. Для выпуска из этого репозитория новый ключ создавать не нужно. Приватный ключ не входит в исходники или файлы релиза.

Для независимого форка создайте собственный ключ. Нужны Windows x64, .NET 10 SDK, PowerShell 7, Python 3 и NSIS 3. Запустите в корне исходников:

```powershell
New-Item -ItemType Directory -Force C:\Kot-Keys
pwsh ./Release/new-key.ps1 -PrivateKeyPath "C:\Kot-Keys\release-private.pem"
```

Скрипт обновит публичный ключ в Core/ReleaseKey.cs. Этот файл коммитится. Приватный PEM остаётся **вне репозитория**, хранится с резервной копией и никогда не прикладывается к релизу. Для всех будущих обновлений используйте тот же ключ.

**У независимого форка после замены ключа другой издатель.** Официальная сборка не примет его архивы после смены ключа. Один раз соберите и вручную установите собственную первую сборку с новым ключом. После этого будущие версии будут обновляться автоматически. Это защита от подмены издателя.

## 3. Сделайте свою первую сборку и установщик

```powershell
pwsh ./Release/release.ps1 -Key "C:\Kot-Keys\release-private.pem" -Repository "USERNAME/kot"
```

В artifacts появятся:

- Kot-Setup-0.4.1-Windows-x64.exe: установщик NSIS.
- Kot-Client-0.4.1-beta-Windows-x64.zip: подписанный пакет для автообновления и portable.
- SHA256SUMS.txt: контрольные суммы.

Закройте старую программу и вручную запустите установщик этой собственной сборки. Номер первой собственной сборки может оставаться 0.4.0. Прежние настройки и HWID сохранятся. Удаление приложения сохраняет профиль в LocalAppData; удаляет только перечисленные файлы программы и отключает её автозапуск.

## 4. Настройте GitHub Actions

Для независимого репозитория в Settings -> Secrets and variables -> Actions -> New repository secret создайте `KOT_RELEASE_SIGNING_KEY`. В официальном репозитории этот шаг уже выполнен. Значение: полное содержимое вашего приватного PEM, включая BEGIN/END. Не вставляйте ключ в код, README или открытый issue.

Workflow .github/workflows/release.yml запускается при push тега v*. Он проверяет Core, собирает Windows x64, подписывает архив, создаёт NSIS EXE и публикует GitHub Release. Для ручной проверки доступен Run workflow, который создаёт Actions artifacts без публикации релиза.

```powershell
git add .
git commit -m "Prepare kot. 0.4.1"
git tag v0.4.1
git push origin main
git push origin v0.4.1
```

В репозитории должна быть включена работа Actions. Настройка permissions.contents: write уже есть. Выпускайте обычный релиз: **не Draft и не Pre-release**, иначе автоматический канал его не выберет. Суффикс beta в имени ZIP сохранён для совместимости и не требует галочки Pre-release.

## 5. Как выпускается следующая версия

Поменяйте версию одинаково в Core/ClientIdentity.cs, Windows/Kot.Windows.csproj и Windows/app.manifest; обновите README и проверки. HTML содержит запасную версию для просмотра без native bridge; при работе приложение передаёт версию из ClientIdentity. Например, следующая версия 0.4.2:

```powershell
git add .
git commit -m "Release 0.4.2"
git tag v0.4.2
git push origin main
git push origin v0.4.2
```

Не удаляйте публичный ключ из Core и не создавайте новый приватный ключ для каждой версии.

## 6. Как работает приложение

В Настройки -> Обновления включите автоматическое скачивание и установку. При запущенном приложении проверка выполняется примерно раз в сутки; есть ручная проверка. Проверяется новый номер версии, точное имя Windows ZIP, HTTPS, ограничения размера, RSA-подпись и SHA-256 всех файлов. GitHub API latest выбирает обычные опубликованные релизы.

При новой версии клиент скачивает ZIP, завершает свой VPN и ping-процессы, заменяет файлы в своей папке и запускает новую версию. Если VPN был включён, пробует восстановить соединение. Если замена или запуск интерфейса не удались, выполняется откат. Сторонние программы и VPN не останавливаются. Контролируется готовность интерфейса, а не доступность VPN-провайдера после запуска.

## 7. Проверка перед публичным выпуском

На Windows вручную установите свою 0.4.0, выпустите тем же ключом 0.4.1 и проверьте обновление при подключённом VPN, сохранение HWID/профиля, ярлыки, автозапуск, удаление. Проверьте отказ при испорченном ZIP и работу при недоступном GitHub. Такие нативные проверки не запускались на Linux-хосте, где подготовлена присланная сборка.

Установщик пока не имеет Windows Authenticode-сертификата. RSA-подпись пакета защищает обновления и не устраняет предупреждение SmartScreen. Падение ядра без kill switch может оставить прямой доступ к сети. При аварийном отключении питания во время замены сохраняются резервные файлы/журнал, но полного автоматического восстановления этого случая пока нет.
