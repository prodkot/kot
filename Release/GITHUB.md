# Выпуск версии

1. Подготовь и протестируй Beta в GitHub Actions по [инструкции для Beta](DEVELOPMENT.md). Для ревизии кандидата должны пройти оба workflow, включая реальные Windows-проверки WebView2, TUN и подписанного установщика. Сохрани ссылки на результаты. Если после Beta изменились код клиента, зависимости или способ упаковки, проверь эти изменения в новой Beta.
2. Запиши изменения в `Release/NOTES.md` и `CHANGELOG.md`.
3. После успешного тестирования Beta получи явное разрешение владельца проекта на стабильный выпуск этой версии. Для стабильной версии сохрани базовый номер и очисти `KotChannel` и `KotPrereleaseNumber` в `Directory.Build.props`. Сверь производные версии клиента, интерфейса, Windows и установщика по [правилам передачи Setup](BUILD-IDENTITY.md).
4. Запусти `python Tests/repository.py`, проверки из [docs/BUILD.md](../docs/BUILD.md) и CI pull request. Проверь итоговый стабильный Setup на ветке PR через **Windows release** с выключенной публикацией. После успешных проверок и разрешения на слияние слей PR.
5. Для разрешённого выпуска открой **Actions → Windows release → Run workflow**, выбери ветку `main`, включи галочку **«Опубликовать новую версию из main в Releases»** и запусти workflow. После сборки и проверок он создаст тег `vНОМЕР` на том же коммите и опубликует установщик.

При выключенной галочке ручной запуск только собирает и проверяет установщик. Публикация вручную разрешена только из `main`. Существующий тег не перезаписывается. Тот же разрешённый выпуск можно опубликовать отправкой тега `vНОМЕР` на проверенном коммите `main`. Отправка тега запускает публикацию автоматически и требует тех же результатов Beta и явного разрешения владельца. Заранее создавать страницу релиза не нужно.

Перед сборкой workflow проверяет совпадение тега с версией клиента и принадлежность публикуемого коммита истории `origin/main`. Тег на неслитой ветке отклоняется. Для проверки истории checkout получает все коммиты; предварительная сборка PR без публикации остаётся доступной.

В сборках `v0.8.0-xray.N` внутренняя версия клиента тоже `0.8.0`. Пользователям этих сборок нужно установить финальный `v0.8.0` новым Setup вручную: встроенный обновлятор предлагает только более высокий номер версии.

Workflow соберёт Setup и подпишет манифесты установщика и вложенного пакета RSA-ключом `KOT_RELEASE_SIGNING_KEY` из GitHub Secrets. Сам файл `.exe` выпускается без Authenticode, поэтому Windows может показать предупреждение SmartScreen. Workflow публикует один установщик и берёт текст страницы релиза из `Release/NOTES.md`.

Приватный ключ хранится вне репозитория. Его публичная часть уже закреплена в клиенте. Не заменяй ключ при обычном обновлении: предыдущие клиенты не примут новую подпись.

Для локальной проверки упаковки подписанного Setup на Windows нужны NSIS 3, Python 3, .NET 10 SDK, PowerShell 7 и Visual Studio 2022 или новее с компонентом **Desktop development with C++** для нативной программы распаковки и небольшой DLL оформления установщика:

```powershell
pwsh ./Release/release.ps1 -Key 'C:\private\kot-release.pem'
```

В `artifacts` останется только Setup. ZIP используется внутри сборки и встраивается в Setup один раз, отдельно не публикуется. NSIS содержит собственные страницы и небольшую нативную DLL оформления, шрифт Manrope, программу распаковки NativeAOT и команды ярлыков и удаления; второго комплекта файлов приложения в нём нет. Перед публикацией Setup повторно проверяется клиентским валидатором и нативной программой распаковки.

В CI сборка также проверяет обновление этим Setup через настоящий updater версии 0.6.1 с запуском нового WebView2. Локальная сборка не запускает эту проверку над обычным аккаунтом разработчика. Её можно выполнить отдельно в чистом тестовом аккаунте Windows через `Release/setup-checks.ps1 -Setup <exe> -Extractor <native-exe> -Publish <publish-folder> -Version <version> -LegacyUpdate`.
