# Проверка 0.4.0, 7 октября 2026

Исправлены: прежнее обновление только скачивало архив; теперь есть автоматическая установка, остановка собственного ядра, перезапуск и проверка готовности интерфейса. При обработанной ошибке старые файлы восстанавливаются. Добавлены проверка точного размера загрузки, отказ от prerelease, проверка версии и всех путей до записи, блокировка стороннего запуска приложения во время замены. Исправлены конфликт файла и папки в ZIP и в установленной папке, повторные действия кнопок и отключение отсутствующей задачи автозапуска.

180 Core-проверок и браузерные сценарии пройдены. Подпись реального архива проверена опубликованным Core; Windows-сборка и NSIS-установщик скомпилированы. Подробности в VALIDATION.txt. Это обзор кода и регрессионные проверки, а не полный пентест sing-box/WebView2 или тест сетевых утечек.

Остаются ограничения: весь интерфейс работает с правами администратора; portable-файлы в пользовательской папке могут быть изменены процессами того же пользователя; kill switch отсутствует; прерывание обновления выключением питания не имеет полной автоматической процедуры восстановления. Недоделанный журнал и резервные файлы сохраняются. Нативный Windows-сценарий обновления и установщика требует отдельной проверки.

RSA-подпись архивов и Windows Authenticode различаются. Установщик не подписан сертификатом Windows-издателя, поэтому SmartScreen может предупреждать. Ключ издателя нужно хранить вне Git и публикуемых файлов. Для перехода на собственный ключ нужна одна ручная установка сборки с новым публичным ключом.

## Предыдущий аудит и исходные находки

# Аудит безопасности kot.

Дата: 7 октября 2026. Проверена версия 0.2.1; исправления выпущены как 0.2.2.

**Вывод:** собственный код уже защищает подписки, резервные копии, интерфейс и установку обновлений несколькими независимыми механизмами. Однако считать приложение полностью защищённым рано. Главные оставшиеся риски: повышенные права всего интерфейса, подмена файлов portable-поставки, отсутствие kill switch и возможность подключения к узлам без шифрования транспорта.

Это ограниченный аудит исходников, сборки и зависимостей с регрессионными тестами. Это не сертификация, не полный пентест сторонних библиотек и не испытание сетевых утечек на Windows.

## Исправлено в 0.2.2

### 1. Подписка могла отключить проверку сертификата TLS

**Высокий риск при использовании такого узла.** VLESS/Trojan/Hysteria2 и VMess импортировали allowInsecure/insecure в tls.insecure=true. Интерфейс не требовал отдельного подтверждения. Для обычного TLS это позволяет принять сертификат атакующего при наличии доступа к сетевому пути. Отдельные проверки Reality могут дополнительно защищать его рукопожатие; уязвимость не означает, что все Reality-серверы автоматически взломаны.

Теперь такие URI пропускаются с объяснением. Смешанная подписка сохраняет безопасные узлы. Проверка также выполняется при построении конфигурации обычного туннель, HTTP-пинга, всех кандидатов «Авто» и проверке резервной копии. Ранее сохранённый узел с tls.insecure=true не сможет запустить ядро. Отключить проверку скрытой настройкой нельзя.

Если ваш провайдер выдаёт такие ссылки, понадобится обновлённая конфигурация с правильным сертификатом. Приложение не заменяет это отключением проверки.

Код: Core/Subscriptions.cs, Core/NodeSecurity.cs, Core/Configuration.cs, Core/Profile.cs.

### 2. Загрузка могла зависнуть после HTTP-заголовков

**Средний риск доступности.** HttpClient.Timeout при ResponseHeadersRead охватывал только получение заголовков. Медленный или злонамеренный сервер мог бесконечно удерживать чтение тела, а вместе с ним импорт или фоновое обновление.

Добавлен общий дедлайн 35 секунд, охватывающий все перенаправления и тело ответа. Отмена передаётся в сетевые операции. Cookie-хранилище клиента отключено. Проверка с мгновенными заголовками и зависшим потоком тела завершилась отменой примерно через 35 секунд.

Это поведение HttpClient описано в [документации Microsoft](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpcompletionoption?view=net-10.0).

### 3. Очистка после ошибки обновления могла затронуть чужую папку

**Низкий риск, локальная гонка файловой системы.** Если после предварительной проверки существования кто-то создавал папку назначения, Directory.Move завершался ошибкой. Обработчик ошибки пытался удалить эту папку, хотя сам установщик её не создал.

Теперь удаление папки назначения разрешено только после успешного переноса собственной подготовленной сборки. Изменение проверено просмотром кода и компиляцией; гонка на реальной Windows не воспроизводилась. Это не полное устранение всех возможных локальных гонок или подмен файлов в доступной для записи папке.

Код: Windows/Updates.cs.

## Дополнительное усиление

- WebView2 запрещает навигацию вложенных фреймов, host objects и стандартные JS-диалоги. CSP явно запрещает frame-src/object-src. Проверки origin и сообщения, запрет внешних окон, загрузок и разрешений уже существовали.
- При чтении ZIP дополнительно сверяется фактическое число распакованных байтов для манифеста, подписи и хешируемых файлов. Тесты отвергают архивы с поддельными размерами. В используемой .NET такие примеры отвергались и прежними проверками; доказанной ZIP-бомбы здесь не установлено. Это усиление, а не заявление о найденной эксплуатируемой уязвимости.
- Очистка слишком большого открытого буфера резервной копии выполняется и при отказе экспорта.
- Маскирование журнала сохраняет разные наборы ключей для узлов с одним ID. Раньше повтор ID мог исключить новый набор из зарегистрированных для маскирования данных. Дополнение проверено компиляцией; нативный буфер обмена Windows здесь не запускался.

## Открытые риски и приоритеты

### P1. Весь интерфейс запущен администратором

Манифест Kot.exe требует requireAdministrator. WebView2, обработчики интерфейса, импорт и работа с файлами находятся в том же повышенном процессе. Задача автозапуска использует HighestAvailable.

Portable-сборка обычно находится в Downloads/Desktop или другой папке, доступной для записи обычному процессу пользователя. Такой процесс может подменить Kot.exe, внешние DLL, sing-box.exe или ui/app.js. Последующий запуск с повышенными правами, включая уже созданную задачу, может выполнить подменённый код с этими правами. Это локальная предпосылка, а не доказанный удалённый взлом через название сервера.

Подпись ZIP защищает импорт обновления; она не проверяет заново установленную папку при каждом запуске. Самопроверка EXE не защищает от замены самого EXE.

**Нужное решение:** интерфейс без повышения; операции TUN в отдельном минимальном процессе или службе с проверяемым IPC; установка исполняемых файлов в защищённую папку с корректными ACL. Проверка файлов при запуске может быть дополнительной мерой, но не заменяет эту архитектуру. В 0.2.2 архитектура не изменена.

[Microsoft рекомендует WebView2-хост без повышения и выделение привилегированных операций](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security).

### P1. Нет kill switch

strict_route действует, пока ядро работает. После остановки ядра или между попытками восстановления приложение не устанавливает постоянный запрет обычного интернета. Поэтому гарантии «никакой трафик не уйдёт напрямую при сбое туннель» нет.

Нужна отдельная политика Windows Filtering Platform или корректно управляемого firewall, покрывающая IPv4/IPv6, DNS, обновление правил, аварии и восстановление. Испытание требует Windows и наблюдения реального трафика. В этом аудите такой гарантии не получено и kill switch не добавлен.

### P1/P2. Возможны узлы без шифрования туннель-транспорта

Парсер допускает VLESS security=none. В сочетании с VLESS encryption=none это не даёт шифрования самого туннель-транспорта. Также стоит ограничить намеренно нешифрующие режимы VMess и Shadowsocks. HTTPS внутри такого соединения защищает свой контент отдельно, но не превращает весь туннель в зашифрованный.

0.2.2 запрещает отключение проверки сертификата, но не вводит полный запрет всех нешифрующих режимов. Для личного использования выбирайте VLESS TLS/Reality или другой протокол с включённой криптографической защитой. Продуктовая доработка: безопасная политика по умолчанию и явное предупреждение/отказ для нешифрующих узлов.

### P2. Временные конфигурации содержат ключи открытым текстом

runtime.json и временные конфиги пинга записываются в LocalAppData/KotVPN для запуска ядра. Удаляются после успешного подключения/остановки и при последующем запуске. После жёсткой аварии могут оставаться на диске до следующего старта.

Основной профиль и HWID защищены DPAPI CurrentUser. Однако DPAPI не является защитой от произвольного вредоносного процесса с правами того же пользователя. Нужны проверяемые ACL и уменьшение времени жизни открытых конфигураций; возможность передачи конфигурации без постоянного файла следует исследовать отдельно.

### P2. Сторонние зависимости ядра требуют контроля

Из Windows sing-box.exe извлечены Go build info: sing-box 1.14.2, Go 1.26.8, 135 связанных Go-модулей. Сверка с OSV обнаружила совпадения у 6 модулей:

| Модуль | Версия | Что требует проверки |
|---|---|---|
| google.golang.org/grpc | 1.79.1 | HTTP/2 DoS, серверные/xDS ошибки |
| golang.org/x/crypto | 0.54.0 | SSH DoS, серверная SSH-авторизация, старый OpenPGP |
| github.com/go-chi/chi/v5 | 5.2.5 | middleware.RealIP и доверие к заголовкам |
| github.com/go-jose/go-jose/v4 | 4.1.3 | ошибки JWE-дешифрования |
| github.com/insomniacslk/dhcp | pseudo-version 20260220 | обработка повреждённого DHCP/IPv4 |
| golang.org/x/mod | 0.37.0 | проверка sumdb, не обычная маршрутизация туннель |

**Это совпадения версий, а не шесть подтверждённых эксплойтов kot.** В официальном EXE нет build tag with_grpc: транспорт gRPC использует v2raygrpclite, а не показанный уязвимый gRPC-Go transport. Конфигурации kot. не включают SSH/Tailscale SSH, DHCP DNS, ACME/JWE, xDS, отдельный gRPC server/API. Достижимость соответствующих функций всех транзитивных зависимостей не проверена полным анализатором вызовов. Возможны дополнительные пути, поэтому объявлять все совпадения ложными тоже нельзя.

Пример первичного advisory: [gRPC-Go HTTP/2 memory exhaustion](https://github.com/grpc/grpc-go/security/advisories/GHSA-vp52-pcj8-j9qc). Требуется контролировать исправленные стабильные релизы ядра и повторять проверку. Ядро в 0.2.2 оставлено прежним, с проверкой совпадения байтов. Оно не объявляется полностью проверенным по CVE.

NuGet-проверка прямых и транзитивных пакетов Windows-проекта не вернула известных уязвимых пакетов на дату аудита. Это не проверка установленного у пользователя WebView2 Runtime, нативного libcronet.dll или всех компонентов Windows/.NET. OSV для stdlib Go 1.26.8 не вернул advisory. Данные версий и IDs приложены в отдельном JSON.

### P3. Локальный прокси без авторизации и идентификация устройства

Служебный mixed-прокси слушает только 127.0.0.1, но не требует пароль. Другие локальные процессы могут его использовать; доступа из LAN конфигурация не открывает. Clash API для «Авто» также только loopback, с отдельным случайным секретом.

HWID отправляется провайдеру по явной настройке, включённой по умолчанию. Это стабильный app-specific hash MachineGuid, а не сырой MachineGuid/MAC. Он всё равно позволяет провайдеру узнавать устройство между запросами; хеш не означает анонимность. Заголовки не пересылаются на другой HTTPS origin и не восстанавливаются при возвратном перенаправлении.

## Что проверено положительно

- HTTPS подписок и перенаправлений; запрет downgrade в HTTP и credentials в URL; лимиты тела, строк, длины URI и числа узлов.
- Названия серверов выводятся через textContent, не HTML. Подписка с HTML-похожим названием не выполняет скрипт. CSP запрещает внешнюю сеть интерфейсу.
- Windows bridge проверяет точный origin, JSON и разрешённые действия; произвольного shell/eval API не найдено. Запуск ядра использует абсолютный путь и отдельные аргументы.
- Основной профиль/HWID под Windows DPAPI; резервные копии AES-256-GCM, PBKDF2-SHA256 300000, случайные salt/nonce, аутентификация заголовка. Пароль и модификация копии проверяются.
- Подписанные ZIP: закреплённый RSA-ключ, SHA-256 каждого файла, запрет лишних файлов, опасных путей, symlink, старой версии. Частный ключ в выдаваемые архивы не попадает.
- Логи ограничены в памяти и маскируются при копировании; сырые журналы на диск не сохраняются кодом kot. Это не гарантия очистки Windows crash dump или логов стороннего провайдера.
- Проверка состояния через HTTPS через выбранный прокси, без прямого fallback. Это проверка работоспособности, не тест всех возможных утечек.

126 утверждений C# прошли, включая TLS-политику, старый профиль/Auto, отключение небезопасных URI, перенаправления/HWID, криптографию копий, подписи ZIP, неверные размеры и реальный общий таймаут тела.

## Дополнение: функции 0.3.0

Это дополнение к аудиту 0.2.1/исправлениям 0.2.2, а не новый полный аудит зависимостей. Исправления 0.2.2 сохранены. Шрифт Manrope поставляется локально с OFL, CSP разрешает только локальные шрифты и по-прежнему запрещает сетевые запросы из WebView.

Локальный Clash API включён также для ручного выбора сервера. Он слушает только 127.0.0.1, требует случайный 256-битный Bearer-secret, ограничивает CORS локальным интерфейсом. Секрет не отправляется в frontend. Чтение статистики ограничено 2 секундами и 2 МБ; интерфейсу передаются максимум 300 соединений. Назначения соединений видимы пользователю намеренно; путь процесса и имя пользователя из processPath отбрасываются. Журнал перед показом и экспортом проходит существующее скрытие секретов.

Онлайн-обновление принимает только HTTPS, запрещает понижение до HTTP, ограничивает перенаправления, размеры и полное время загрузки. Метаданные источника не заменяют закреплённую RSA-подпись ZIP. Установка проверяет каждый файл, более новую версию и совпадение версии ZIP с источником; очистка удаляет только созданные этой операцией файлы/папки. Фоновая проверка не устанавливает обновление без нажатия пользователя. Хостинг пока не подключён.

Повышенные права GUI, подмена файлов portable-поставки, отсутствие kill switch и возможность незашифрованного транспорта остаются прежними границами. Реальные Windows API, сетевые утечки и нативная установка обновления в этом окружении не испытаны.


## Дополнение: HWID в 0.3.1

Это проверка изменений HWID, а не новый аудит зависимостей. Алгоритм, соль и DPAPI-файл существующего HWID не меняются. Новое имя `kot. windows (0.3.1)` передаётся как `x-device-model`, версия не добавляется в `x-hwid`. Совместимый User-Agent содержит имя/версию приложения и маркер v2rayN, без HWID. Переключатель передачи HWID и защита от передачи заголовков на другой origin сохранены.

Окно устройства запрашивает HWID только после явного открытия. Native bridge принимает readHwid/copyHwid только с доверенной локальной страницы; копирование получает ID из DeviceIdentity, без принятия текста из страницы. ID не включён в периодический snapshot, при закрытии окна поле очищается, поздний ответ после закрытия игнорируется. DeviceIdentity регистрирует ID для маскирования журнала. В буфере обмена ID остаётся до замены пользователем или другим приложением; процессы с доступом к буферу могут его прочитать. Это намеренное действие кнопки копирования.

Данные устройства остаются доступны провайдеру только через существующую настройку передачи HWID. Просмотр/копирование не делает сетевого запроса. Статические проверки и эмуляция UI не заменяют испытание DPAPI/буфера обмена на Windows или отображения метаданных в конкретной панели.
