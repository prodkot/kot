# Аудит Windows-интеграции kot. 0.8.3

Дата: 8 ноября 2026. Изменения входят в [PR #51](https://github.com/prodkot/kot/pull/51), ветка `ui/p51-polish`. Публичного релиза, тега и слияния в main нет. Версия остаётся 0.8.3. Исследование и тесты не обращались к пользовательскому ПК и его подпискам.

## Главные выводы

1. **Причина старого деинсталлятора подтверждена кодом.** Раньше `Uninstall.exe` создавался NSIS только при полной установке и не входил в подписанный ZIP автообновления. Клиент и `DisplayVersion` могли стать 0.8.2, а исполняемый деинсталлятор, его интерфейс и список удаляемых файлов оставались от 0.8.0. Теперь актуальный `Uninstall.exe` создаётся до подписи пакета и обновляется тем же транзакционным механизмом, что и клиент.
2. **Подтверждены дефекты проверки автозапуска.** Раньше наличие включённой задачи считалось достаточным. Неверный путь, рабочая папка, пользователь, триггер или условия не проверялись. Все копии клиента используют одно имя задачи для пользователя, поэтому запуск тестовой/перенесённой копии мог изменить её действие. Теперь проверяется определение задачи; включённая повреждённая задача восстанавливается установленной копией; посторонняя копия не может перенастроить автозапуск.
3. **На ПК подтверждено отсутствие штатной задачи автозапуска для учётной записи диагностики.** Отчёт v3 прочитал задачи через CIM и COM без ошибок: `KotVPN-<текущий SID>` отсутствует, служба Schedule работает. Найдена только задача тестового семейства с `TimeTrigger`, другой копией EXE версии 0.8.0, без `--startup` и рабочей папки. Она не запускает установленный клиент при входе. Установлены клиент и регистрация 0.8.2, деинсталлятор 0.8.0, процесса нет. Почему штатная задача не была создана или исчезла, отчёт не устанавливает. Это относится к учётной записи диагностического процесса; при UAC с данными другого администратора она может отличаться от пользователя рабочего стола. Windows CI не заменяет настоящий выход и повторный вход пользователя.
4. **Личные данные сохраняются.** Деинсталлятор не удаляет LocalAppData-профиль, подписки, HWID и статистику. Проверки используют только синтетические данные отдельного Windows runner. Сетевое ядро, маршрутизация и логика Kill Switch в этой правке не заменялись.

## Как устроен автозапуск

Источник: [Windows/Startup.cs](https://github.com/prodkot/kot/blob/ui/p51-polish/Windows/Startup.cs), [Program.cs](https://github.com/prodkot/kot/blob/ui/p51-polish/Windows/Program.cs), [MainWindow.cs](https://github.com/prodkot/kot/blob/ui/p51-polish/Windows/MainWindow.cs).

| Параметр | Фактическая реализация |
|---|---|
| Механизм | COM `Schedule.Service`, корень Планировщика задач |
| Имя | `KotVPN-<SID текущего пользователя>` |
| Триггер | `LogonTrigger` только этого пользователя, включён, без задержки и границ времени |
| Действие | Полный путь к установленному `Kot.exe`, отдельный аргумент `--startup` |
| Рабочая папка | Каталог клиента |
| Сессия | `InteractiveToken`: вошедший в Windows пользователь |
| Права | `HighestAvailable`; манифест клиента требует администратора |
| Повторный запуск | `IgnoreNew`; дополнительно клиент использует пользовательский mutex |
| Условия | Не требует простоя или сети, допускает работу от батареи |
| Лимит времени | `PT0S`, без ограничения |
| Запуск по требованию | Разрешён, `StartWhenAvailable=true` |
| Реестр Run / папка Startup | Текущий клиент их для автозапуска не создаёт |

Модель прав описана в [Microsoft Task Scheduler security contexts](https://learn.microsoft.com/en-us/windows/win32/taskschd/security-contexts-for-running-tasks). `HighestAvailable` не превращает обычного пользователя в администратора. Вход под обычной учётной записью и UAC с данными другого администратора требуют отдельного теста: SID, профиль и задача могут принадлежать другой учётной записи. Эта работа не заявляет поддержку запуска административного клиента без соответствующих прав.

### Синхронизация с настройками и несколько копий

- При инициализации установленный клиент проверяет уже включённую задачу и исправляет неверное определение. Отсутствующую или явно выключенную в Windows задачу автоматически не включает.
- При открытии настроек приложение заново считывает состояние Windows, а не показывает только сохранённый `profile.Startup`.
- Запись в списке «Автозагрузка приложений» Windows не является достаточным подтверждением этой задачи: старые Run/StartupApproved-записи проверяются диагностикой отдельно, текущая реализация использует Планировщик.
- Здоровое состояние означает совпадение EXE, рабочей папки, аргументов, SID, триггера, principal и условий. Наличие EXE также проверяется.
- Владельцем настройки считается EXE из `HKLM` регистрации установленного приложения. Копия из другой папки получает понятную ошибку вместо перехвата задачи.
- Setup после регистрации нового пути исправляет включённую задачу текущего пользователя. При выключенной задаче сохраняет выключенное состояние.
- Деинсталлятор удаляет задачи с именем kot, действие которых указывает ровно на удаляемый EXE, в том числе задачи других пользователей. Чужие профили не открывает.
- Удаление старой копии не удаляет регистрацию, ярлыки или задачу новой копии. Оно очищает только задачи, указывающие на старый путь.

Ограничения: это не полная изоляция переносных копий. Профиль, mutex и машинные WFP-фильтры остаются общими по существующей схеме. Текущий KotQA запускает отдельные сетевые тесты, а не регистрирует клиент в автозапуске; поведение неизвестных старых сборок KotQA на ПК не установлено. При переносе установки задачи других пользователей не мигрируют автоматически: они исправляются при запуске установленного клиента соответствующим пользователем. Полная многопользовательская миграция требует отдельного сценария.

### Не исчезает ли процесс после запуска

[StartupEvidence.cs](https://github.com/prodkot/kot/blob/ui/p51-polish/Windows/StartupEvidence.cs) записывает один небольшой `startup-lifecycle.json`: версия, PID, сессия, время, стадия запуска и готовность UI/трея. Профили, пути, подписки и пароли туда не попадают. Ошибка записи не мешает запуску. Обычный ручной запуск не заменяет запись автоматического запуска.

Маркер создаётся после захвата mutex. Если процесс не дошёл до этой точки, например Windows не смогла запустить EXE, нужны сведения Планировщика и события Windows. При аварийном завершении последняя стадия может остаться `starting` или `ready`, поэтому её сопоставляют с живым процессом и временем. `trayVisible` означает состояние компонента приложения, а не визуальное доказательство иконки в оболочке Explorer.

[Tests/startup-installed.ps1](https://github.com/prodkot/kot/blob/ui/p51-polish/Tests/startup-installed.ps1) в одноразовом Windows runner включает автозапуск штатной командой клиента, запускает реальную задачу через `RunEx` в интерактивной сессии, ждёт готовности WebView, проверяет путь процесса и сессию, наблюдает работу ещё 15 секунд и проверяет штатное завершение. После выключения/повторного включения сценарий повторяется. Отдельно проверяются внешнее выключение задачи, переустановка, перенос пути, конфликт с копией и удаление старой копии.

**Это запуск Планировщиком по требованию, не срабатывание LogonTrigger после нового входа.** Различие следует из [документации RunEx](https://learn.microsoft.com/en-us/windows/win32/taskschd/registeredtask-runex) и [LogonTrigger](https://learn.microsoft.com/en-us/windows/win32/taskschd/logontrigger). Результат реального входа на ПК остаётся открытым.

## Установщик, автообновление, деинсталлятор

Код исправления: [Release/release.ps1](https://github.com/prodkot/kot/blob/ui/p51-polish/Release/release.ps1), [Installer/Kot.nsi](https://github.com/prodkot/kot/blob/ui/p51-polish/Installer/Kot.nsi), [installer-files.py](https://github.com/prodkot/kot/blob/ui/p51-polish/Release/installer-files.py). Тесты: [setup-checks.ps1](https://github.com/prodkot/kot/blob/ui/p51-polish/Release/setup-checks.ps1), [InstallerTests.cs](https://github.com/prodkot/kot/blob/ui/p51-polish/Tests/InstallerTests.cs).

Новый порядок сборки:

1. Собрать клиент 0.8.3 и список его файлов.
2. NSIS-генератор создаёт настоящий `Uninstall.exe` 0.8.3 без установки приложения. Проверить PE ProductVersion.
3. Включить деинсталлятор в общий подписанный payload.
4. Собрать Setup и добавить этот же проверяемый payload.

Полная установка и автообновление теперь используют один экземпляр деинсталлятора из подписанного пакета. Если замена файлов откатывается, откатывается и деинсталлятор. Список удаления включает служебные `release.json` и `release.sig`, но не произвольные пользовательские файлы.

| Поверхность версии | Требование и проверка |
|---|---|
| `Core/ClientIdentity.cs` | 0.8.3, источник версии клиента |
| Windows csproj / manifest | 0.8.3 / 0.8.3.0, согласованность при сборке |
| Kot.exe | PE ProductVersion начинается с 0.8.3; версия клиента и подписанного manifest согласованы |
| Setup | Имя 0.8.3, NSIS FileVersion/ProductVersion 0.8.3, числовая версия 0.8.3.0 |
| Uninstall.exe | Создан для 0.8.3, PE ProductVersion проверяется до подписи и после обновления |
| Установленные программы | HKLM DisplayVersion 0.8.3, InstallLocation и UninstallString указывают на текущую установку |
| Updater | Проверяет подпись/manifest/состав; обновляет DisplayVersion только у своей зарегистрированной установки |
| GitHub / публичный канал | Версия 0.8.3 не публикуется этой задачей; CI artifact не является публичным релизом |

Интеграционные сценарии используют настоящие опубликованные 0.8.0, 0.8.1 и 0.8.2. Старый Setup создаёт старый деинсталлятор, затем старый updater устанавливает новый пакет. После запуска нового UI проверяются файлы, версия деинсталлятора, ARP и синтетические данные: непустая подписка, сервер, избранное, профиль маршрутизации, настройки, зашифрованный HWID, статистика и пользовательский файл. Для 0.8.0 и 0.8.2 также проверяется сохранение включённой задачи, для 0.8.1 проверяется сохранение явно выключенной задачи и синхронизация переключателя нового клиента. Также сохраняются прежние проверки миграции с 0.6.1 и 0.7.3 через Setup.

Проверяются повторная установка, Unicode/пробелы в пути, отказ от повреждённого подписанного пакета до замены файлов, поздняя ошибка замены с откатом и восстановление прерванной транзакции при старте. **Общий откат всех действий Windows не реализован:** запись ARP/ярлыков и восстановление автозапуска выполняются после транзакции файлов. Ошибка на этом этапе может оставить уже обновлённые файлы и частично завершённую регистрацию. Установщик сообщает ошибку, повторная установка является путём восстановления. Проверки файлового отката не доказывают атомарность всей установки.

Удаление сначала корректно закрывает текущую зарегистрированную копию и снимает её Kill Switch; при ошибке этих действий удаление останавливается. Устаревшая копия не меняет глобальную сетевую блокировку новой установки. Удаляются принадлежащие пути задачи, известные файлы, актуальные общие ярлыки и ARP-запись. LocalAppData и неизвестные пользовательские файлы сохраняются, поэтому каталог установки может остаться непустым.

Исправленный тестовый Setup остаётся версией 0.8.3. Если уже установлена предыдущая тестовая 0.8.3, применяется ручная установка поверх неё: автоматический канал не предлагает ту же версию как новую. Публичного выпуска для этого не требуется.

Снимок настоящего деинсталлятора из Windows CI: в заголовке отображается «Удаление 0.8.3». Это окно тестовой установки runner, не ПК пользователя.

### Найденное предупреждение зависимости

Windows-сборка выявила NU1903 для NativeAOT ILCompiler 10.0.12. По [Microsoft advisory GHSA-p3jp-9v83-76w9](https://github.com/advisories/GHSA-p3jp-9v83-76w9) затронут .NET Brotli decoder до 10.0.14. SDK закреплён на 10.0.403 с runtime 10.0.14 согласно [официальным release metadata](https://builds.dotnet.microsoft.com/dotnet/release-metadata/10.0/releases.json). Обновляется и встроенный runtime клиента, и toolchain нативного extractor. Это исправление зависимости, не повышение версии приложения. Эксплуатация уязвимости в kot не воспроизводилась и не заявляется.

## Что kot. создаёт в Windows

Таблица отражает собственный код клиента и закреплённое ядро Xray. Она не утверждает отсутствие внутренних следов Windows, WebView2, драйверов и антивируса после удаления.

| Что создаёт или меняет | Зачем | Когда удаляет или восстанавливает | Что может остаться |
|---|---|---|---|
| `%ProgramFiles%\Kot` или выбранная папка | EXE, UI, ядро Xray, Wintun, ресурсы, Uninstall.exe, подписанные метаданные | Известные файлы при удалении; замена при обновлении | Пользовательские файлы; занятые файлы при аварии |
| HKLM64 `...\Uninstall\KotVPN` | Список установленных программ, версия, путь, удаление | При удалении владельца текущей регистрации | При прерванной установке/удалении; старый деинсталлятор до исправления мог повредить чужую регистрацию |
| Общие ярлыки меню «Пуск» в `%ProgramData%` и `%PUBLIC%\Desktop` | Запуск и удаление | При удалении текущей зарегистрированной установки | Закреплённые пользователем ссылки и кеш иконок Windows |
| AppUserModelID `Prodkot.Kot.Client` у процесса/ярлыков | Группировка окна и значок панели задач | Процесс завершается, ярлыки удаляются | Кеш оболочки, пользовательские закрепления |
| Задача `KotVPN-<SID>` | Автозапуск в пользовательской сессии с нужными правами | Выключение в kot; удаление задач по точному пути EXE | Ошибка доступа/удаления, старые осиротевшие задачи; выключенные вручную сохраняются при переустановке |
| `Local\KotVPN-<SID>` mutex и канал команд | Один экземпляр, запросы shutdown/activation | Освобождаются при завершении процесса | Не являются постоянной службой или файлом |
| `%LOCALAPPDATA%\KotVPN\profile.bin`, резервные и recovery-копии | Подписки, настройки, маршрутизация, избранное; DPAPI текущего пользователя | Не удаляются деинсталлятором | Намеренно сохраняются; работают в контексте соответствующего Windows-пользователя |
| `device.bin` | Стабильный зашифрованный HWID | Не удаляется при обновлении/удалении | Намеренно сохраняется. MachineGuid только читается |
| `traffic-history.json`, `traffic-details.json` | Статистика и детализация трафика | По функциям очистки приложения, не деинсталлятором | История, потенциально чувствительные сведения |
| `WebView`, кеши `xray-assets`, `geoip-cidr` | Отображение UI, ресурсы и списки маршрутизации | Кеши обслуживаются компонентами, профиль сохраняется | Кеши, данные WebView, скачанные ресурсы |
| Диагностические файлы, `startup-error.json`, `maintenance-error.txt`, `startup-lifecycle.json` | Разбор ошибок и стадий запуска | По политике соответствующего лога; lifecycle перезаписывает одну запись | Последний сбой или стадия после аварии |
| `update-<guid>.exe` в LocalAppData | Скачанный установщик | Штатный finally обновления | При аварии до очистки |
| `.kot-update-<guid>` внутри установки | Updater/Recovery, пакет, staging, backup, journal, receipts | После commit/успешного rollback; восстановление при следующем старте | При блокировке файлов или неудачном откате сохраняется материал восстановления |
| `%TEMP%\.net` или `DOTNET_BUNDLE_EXTRACT_BASE_DIR` | Извлечение native-библиотек single-file .NET при необходимости | Управляется .NET, отдельной очистки kot нет | Кешы распаковки разных сборок |
| Microsoft WebView2 Runtime и его дочерние `msedgewebview2.exe` | UI; при отсутствии клиент предлагает официальный установщик | UI-процессы завершаются с окружением; общий Runtime kot не удаляет | Runtime, его обновляющие компоненты/регистрация Microsoft |
| Метки целостности SACL в собственных пакетах services | High для zapret, Medium для Telegram | Уходят с удалёнными файлами пакета | У сохраняемых файлов метки остаются; владельцы/DACL не заменяются |
| Отложенные удаления Windows через `MoveFileExW` | Удаление занятых файлов своего пакета после перезагрузки | Windows при перезагрузке | PendingFileRenameOperations до обработки/при ошибке, только свои файлы |
| Экспортированные вручную backup/log/routing-файлы | Выбранное пользователем место сохранения | Только пользователь | Намеренно не удаляются установщиком |
| Временная папка NSIS в Windows Temp | Нативный helper, интерфейс, промежуточный деинсталлятор | При обычном выходе установщика | После аварии установщика |
| Дочерние Kot Updater/Recovery/proxy-watch | Обновление, откат, восстановление системного прокси | После выполнения своей ограниченной задачи | Процесс до завершения; диагностические/временные файлы при аварии |
| `xray.exe`, тестовые/ping-процессы, job object | Сетевое ядро и проверки доступности | Штатная остановка, затем ограниченное ожидание/завершение дерева; kill-on-job-close | Возможные следы драйвера/адаптера, не сохранённая stdin-конфигурация |
| `kot-tun`, Wintun, адреса, маршруты, DNS TUN | Перехват и маршрутизация VPN-трафика | Xray при Close очищает адреса/маршруты/DNS, закрывает сессию/адаптер | При аварии/ошибке очистки возможны следы адаптера и драйверного пакета. Полная очистка Driver Store не заявляется |
| DNS кеш и регистрация DNS TUN-адаптера | Настройки DNS туннеля, предотвращение нежелательной регистрации | Код закрытия ядра восстанавливает свои параметры и сбрасывает кеш | Поведение при жёстком сбое требует физического теста; Windows кеши не равны файлам kot |
| WinINet системный прокси и `system-proxy.bin` | Локальный proxy-режим и сохранение прежних параметров | При отключении, watcher после смерти родителя, следующий запуск; только если параметры ещё принадлежат kot | Если погибли оба процесса, прокси/receipt могут остаться до восстановления |
| Машинные persistent WFP-фильтры Kill Switch | Не выпускать трафик вне защищённого маршрута | Явное выключение и штатный uninstall | После аварии остаются намеренно. Это может блокировать интернет до явного восстановления |
| WFP sublayer kot с постоянным GUID | Группа фильтров Kill Switch | Фильтры удаляются, сам пустой sublayer текущий код не удаляет | Пустой sublayer, сам по себе трафик не блокирует |

| Временный `TgWsProxy_data\config.json` с секретом, логи | Конфигурация запущенного Telegram proxy | Конфиг удаляется при штатной остановке сервиса | После аварии конфиг и логи могут остаться; диагностика автозапуска их не читает |
| Драйверные компоненты Wintun/WinDivert | Работа Xray TUN и опционального winws | Управляются соответствующими компонентами/Windows | Возможные записи Driver Store/драйверов; клиент не удаляет вслепую общие драйверы других программ |

WinINet API обслуживает пользовательские Internet Settings; задача имеет внутренние файлы/TaskCache, которыми управляет Планировщик, kot не правит их напрямую. О запланированном удалении: [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw); о кеше native-библиотек: [single-file deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview).

Собственной постоянной службы SCM `Kot` клиент не создаёт. WinHTTP-прокси и hosts текущий `SystemProxy` не меняет. Отдельного рабочего хранилища kot в ProgramData нет, там находятся общие ярлыки.

Источники по интеграции: [NativeCore.cs](https://github.com/prodkot/kot/blob/ui/p51-polish/Windows/NativeCore.cs), [SystemProxy.cs](https://github.com/prodkot/kot/blob/ui/p51-polish/Windows/SystemProxy.cs), [KillSwitch.cs](https://github.com/prodkot/kot/blob/ui/p51-polish/Windows/KillSwitch.cs), [Store.cs](https://github.com/prodkot/kot/blob/ui/p51-polish/Windows/Store.cs), [закреплённое ядро Xray](https://github.com/prodkot/kot/tree/ui/p51-polish/upstream), [службы](https://github.com/prodkot/kot/blob/ui/p51-polish/docs/SERVICES.md).

### По этапам жизненного цикла

- **Установка:** файлы, общие ярлыки, ARP. Автозапуск сам не включается; уже включённая задача текущего пользователя чинится при необходимости.
- **Запуск:** пользовательский профиль/DPAPI, WebView, mutex, логи, проверка незавершённого обновления и сохранённого прокси, сверка автозапуска. При `--startup` добавляется небольшой lifecycle-маркер.
- **Подключение TUN:** дочернее ядро, Wintun/адаптер/маршруты/DNS. При включённом Kill Switch добавляются блокирующие WFP-фильтры.
- **Подключение proxy:** локальный порт, сохранение предыдущих WinINet-настроек, proxy-watch, установка системного прокси.
- **Отключение:** штатная остановка ядра и принадлежащих соединению ресурсов. Включённый Kill Switch имеет отдельную политику fail-closed, его нельзя считать автоматически снятым из-за отсутствия VPN-процесса.
- **Обновление:** подписанный пакет, транзакционная замена, готовность нового UI, commit либо rollback; текущие данные пользователя сохраняются.
- **Удаление:** остановка владельца установки, снятие блокировки, очистка принадлежащих пути задач и известных файлов/регистрации/ярлыков. Данные пользователя сохраняются.

### Диагностика на ПК

[QA/Startup-Diagnostics.ps1](https://github.com/prodkot/kot/blob/ui/p51-polish/QA/Startup-Diagnostics.ps1) только читает Windows: связанные задачи, действия, триггеры, principal, условия, last/next run, hex-код результата, наличие EXE и версии, связанные события Планировщика/Application, процессы и их живучесть в течение трёх секунд. Не запускает/останавливает клиент, не включает журналы, не меняет реестр/задачи/сеть, не читает профиль/подписки/HWID. Нет сетевых запросов.

В выводе нет полного пути, имени компьютера, пользователя, SID, командной строки или исходных текстов событий. Пути заменены проверками совпадения с зарегистрированной установкой; события представлены ID/временем/числовыми кодами. Недоступный или выключенный журнал отмечается отдельно, это не эквивалент отсутствия ошибки. Скрипт проверяется AST-ограничениями и реальным запуском в Windows PowerShell 5.1.

Первый отчёт с ПК выявил недостаток самой диагностики: единственный способ чтения задач через PowerShell/CIM завершился ошибкой `0x80131501`. Этот HRESULT обозначает общий [SystemException](https://learn.microsoft.com/en-us/dotnet/api/system.systemexception), а не конкретную причину сбоя автозапуска. В v1 терялись типы вложенных исключений, и пустой массив задач можно было ошибочно принять за их отсутствие. Выключенный `TaskScheduler/Operational` означает отключение журнала, а не службы.

В v2 добавлено независимое чтение через COM `Schedule.Service`, включая скрытые задачи в корне, отдельный запрос канонической задачи пользователя и отдельное состояние службы Schedule. `taskRead` различает успешное чтение, частичный результат, отказ и неизвестность; `readErrors` содержит ограниченную цепочку типов/числовых HRESULT без исходных сообщений. Проверки включают реальную скрытую отключённую задачу, отказ CIM с HRESULT `0x80131501`, отказ обоих способов, сохранение определения/времени запуска задачи и отсутствие приватных строк. Диагностика не запускает задачу и не включает журнал. Синтетические ошибки теста не являются диагнозом пользовательского ПК.

Второй отчёт уточнил место ошибки: оба способа доходили до данных действия, затем `Path.GetDirectoryName` внутри диагностики выбрасывал ArgumentException с HRESULT `0x80070057`. Это ошибка обработки пути в скрипте, а не доказанный отказ CIM или службы Schedule. В Windows PowerShell 5.1 такой вызов отвергает, например, путь в кавычках; точное содержимое проблемного пути из отчёта неизвестно. См. [документацию .NET Framework](https://learn.microsoft.com/en-us/dotnet/api/system.io.path.getdirectoryname).

В v3 путь обрабатывается отдельно с перехватом ошибок. Параметры пользователя, триггер и последний результат задачи сохраняются даже при некорректном пути. Отдельные безопасные флаги показывают кавычки, аргументы внутри поля EXE, переменные окружения и совпадение нормализованного кандидата с установленным EXE; это не выдаётся за корректность исходного действия. UNC и сетевые диски не проверяются на наличие файла. Добавлены регрессии с реальной скрытой отключённой задачей с EXE в кавычках и некорректными путями. Содержимое задачи не изменяется. Отсутствие канонической задачи относится к учётной записи диагностического процесса, не автоматически к пользователю интерактивного рабочего стола при запуске под другими административными credentials.

Поле EXE тестовой задачи заключено в кавычки. `literalPathError=0x80070057` относится к обработке такого поля .NET Framework в диагностике, не к последнему запуску Windows. После снятия внешних кавычек кандидат существует (`normalizedExists=true`). Поэтому нельзя объявлять файл отсутствующим или считать кавычки доказанной причиной исторического падения.

В текущем состоянии для учётной записи диагностики нет штатного механизма запуска установленного kot при входе. Само наличие включённой тестовой задачи не доказывает конфликт: она не заменяет нужный LogonTrigger, но её существование само по себе не блокирует другую задачу. Журнал TaskScheduler/Operational выключен, история создания/удаления штатной задачи не получена. Версия 0.8.2 уже сверяла состояние задачи при старте приложения, поэтому наблюдение прежнего включённого переключателя нельзя объяснить утверждением, что синхронизации вообще не было.

### Следующая проверка на ПК

Повторная сборка и четвёртая версия диагностики не требуются. Уже переданный исправленный установщик 0.8.3 содержит нужные изменения; по отчёту на ПК пока остаётся 0.8.2.

1. Установить переданный исправленный 0.8.3 поверх текущей установки, без предварительного удаления.
2. Запустить установленный kot из меню «Пуск» и включить автозапуск в настройках. Если переключатель уже включён, выключить и включить его заново. Проверить, что действие завершилось без ошибки. Это явное включение создаёт штатную задачу; Setup и автоматическое восстановление намеренно не создают отсутствующую задачу без него.
3. При удобном следующем выходе и входе в Windows проверить появление процесса и трея. До ручного запуска kot повторить тот же скрипт v3, чтобы сопоставить задачу, последний запуск, процесс и lifecycle-маркер.

Если UAC требует данные другого администратора, учётную запись нужно учитывать отдельно: задача текущего административного процесса может не относиться к обычному пользователю рабочего стола. На ПК ничего из этих действий удалённо не выполнялось, тестовая задача не удалялась.

После входа, **до ручного запуска kot**, из папки с уже переданным скриптом v3:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Kot-Startup-Diagnostics-v3.ps1 > kot-startup-report-v3.json
```

Редирект создаёт только JSON-отчёт. Содержимое сети и настроек не изменяется. PID, номер сессии, версии и времена остаются в отчёте как необходимые диагностические сведения.

### Матрица реального повторного входа, пока не выполнена

Эти действия не выполняются диагностическим скриптом. Они требуют пользователя и планируются так, чтобы не зависеть от живого соединения с чатом. Для проверки автозапуска падение ядра и Kill Switch не трогаются.

| Сценарий | Ожидаемое наблюдение после нового входа |
|---|---|
| Автозапуск включён штатно | LastRunTime новее входа, правильные действие/пользователь, живой процесс в текущей сессии, готовый UI/трей |
| Автозапуск выключен штатно | Задача отсутствует, новый процесс автоматически не появился |
| Повторное включение и второй вход | Процесс появляется снова и остаётся живым, один экземпляр |
| Обновление/переустановка поверх текущей версии | Состояние автозапуска сохраняется, действие указывает на существующий актуальный EXE |
| Изменение папки установки | Действие и рабочая папка соответствуют новому месту; старая копия не перехватывает задачу |

Порядок разбора: задача не запускалась -> триггер/SID/служба/журнал; запускалась с ошибкой -> код результата и события; результат успешный, процесса нет -> lifecycle/события приложения/дубликат процесса; процесс есть в другой сессии -> principal/UAC; процесс живой без готового UI -> WebView/стадия инициализации. Нулевой LastTaskResult сам по себе не считается доказательством работоспособности.
