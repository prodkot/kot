## Зависимости и оставшиеся риски

NuGet vulnerability feed проверен для YamlDotNet 18.1.0, ZXing.Net 0.16.11 и WebView2 SDK 1.0.4314.35. Найденная запись YamlDotNet относится к версиям до 4.3.2 включительно; она не совпадает с используемой версией. Это не оценка установленного у пользователя Evergreen Runtime.

`govulncheck v1.9.0 -mode=binary` сообщил три advisory в модулях Xray: [GO-2026-6866](https://pkg.go.dev/vuln/GO-2026-6866), [GO-2026-6860](https://pkg.go.dev/vuln/GO-2026-6860), [GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932). Затем выполнен source-анализ `./main` точного Windows-исходника: **0 достижимых уязвимостей; 3 advisory в требуемых модулях без обнаруженной цепочки вызовов**. Это результат анализа достижимости, не доказательство невозможности эксплуатации при любых изменениях сборки. Никаких исключений или suppressions в сканер не добавлено. Новый `Tests/xray_dependencies.py` включён в интеграционный и release CI.

У upstream уже есть [Xray 26.10.31](https://github.com/XTLS/Xray-core/releases/tag/v26.10.31), в том числе с изменением MPTCP из-за Linux kernel advisory. Здесь сохранён 26.10.21: применимость описанного Linux-сценария к Windows-клиенту не подтверждена, а замена TUN-ядра без реальных TUN/WFP-регрессий добавляет непроверенную переменную. Следующий core upgrade следует оценить и проверить отдельно до финального выпуска.

Host/UI остаётся повышенным; перенос ядра в отдельную службу — архитектурная рекомендация с миграционными рисками. Гарантия отсутствия DNS/IPv6-утечек не выдана. Внешний Setup по существующей документации не имеет Authenticode; встроенная RSA-подпись пакета защищает другую часть цепочки доверия. Производственный ключ издателя не запрашивался и не использовался.

GitHub API вернул пустой список repository rulesets. Чтение legacy branch protection для main вернуло 403 `Resource not accessible by integration`; отсутствие legacy-защиты этим не доказано. Проверка истории внутри workflow защищает от случайного выпуска неслитого тега при неизменённом workflow. От участника, способного переписать сам workflow в теге, нужна независимая политика GitHub: ограничения создания release-тегов и защищённое окружение ключа подписи. Настройки аккаунта и Secrets не изменялись; их достаточность не подтверждена.

## Обязательные действия на отдельной Windows-машине

1. Выполнить полный Core-набор и стандартный WindowTests в чистом тестовом аккаунте с правом создания ссылок. Существующая fixture миграции профиля намеренно отказывается работать поверх пользовательского KotVPN-каталога.
2. Проверить старые профили/backup 0.6.x и 0.7.x, HWID, избранное, активную подписку, DPAPI и rollback после прерывания установки.
3. Собрать закреплённый Xray, затем выполнить `Kot.WindowTests.exe --tunnel-test <xray.exe>` с `wintun.dll`. Проверить crash ядра и приложения, постоянство WFP и намеренное отключение Kill Switch.
4. Захватить IPv4/IPv6/DNS-трафик на физическом адаптере при старте, смене сервера, аварии, потере сети, переходе Wi-Fi/Ethernet, сне/возобновлении и перезагрузке; отдельно учесть разрешённые direct-маршруты и DHCP.
5. Выполнить полный release workflow в режиме сборки без публикации с настоящим ключом издателя: подпись и hashes, Setup install/reinstall/uninstall, недостаток места, блокировка файлов, отказ запуска новой UI и возврат старой версии.
6. Проверить tray, mini-player, startup/UAC, реальные WebView2 crashes и все UI-действия с настоящим host. Повторить HTTPS-отмену на скачивании, геобазах и валидации большой подписки, включая закрытие приложения.
7. Провести испытания на нескольких реальных Windows 10/11 x64 и провайдерах: REALITY, XHTTP, IPv6-only/dual-stack, native TUN и system proxy. Браузерные fixtures этих испытаний не заменяют.

Финальный статус: код исправлений подготовлен к PR; выпуск 0.8.0 нельзя считать полностью готовым, пока перечисленные проверки не дадут реальные результаты. Полный объём аудита не является формальным доказательством отсутствия остальных ошибок.
